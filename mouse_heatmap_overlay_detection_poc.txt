MOUSE HEATMAP BASED OVERLAY DETECTION
Proof of Concept (POC) Technical Document

Version: 1.0
Purpose: POC planning and implementation reference


1. EXECUTIVE SUMMARY
====================

The current overlay-detection approach primarily uses keyboard and window/focus-related events to identify suspicious overlay usage. That approach can detect several common cases, such as shortcut-based overlay opening or focus changes, but it has an important limitation:

- An overlay may remain open before the test starts.
- The overlay may operate in an undetectable/no-focus-shift mode.
- The overlay may not cause an observable browser focus change.
- The user may interact with the overlay without generating a useful keyboard/focus signal inside the test application.

This POC proposes a second, complementary approach based on MOUSE HEATMAP ANALYSIS.

The basic idea is:

    Collect mouse movement/interaction data during the test
                  ↓
    Map the activity to screen/test regions
                  ↓
    Build a spatial heatmap
                  ↓
    Identify regions with unusual mouse activity
                  ↓
    Combine the spatial signal with timing and test context
                  ↓
    Produce suspicious-region / suspicious-behavior output

The objective is NOT to claim that a particular pixel region definitely contains an overlay.

The objective is to determine whether mouse interaction patterns reveal a region or behavioral pattern that is inconsistent with normal interaction with the test UI.


2. PROBLEM STATEMENT
====================

The existing event-based model observes events generated by the test application/browser.

Typical useful signals include:

- keyboard shortcuts
- keydown/keyup events
- focus/blur
- typing behavior
- answer length changes
- copy/paste-related behavior
- question navigation

However, an external overlay can be designed so that:

1. It does not steal browser focus.
2. It does not trigger a blur/focus transition.
3. It is opened before the test begins.
4. It remains open throughout the test.
5. The user interacts with it in a way that produces little or no detectable keyboard signal in the test page.

Therefore, a second source of behavioral evidence is required.

Mouse activity provides a spatial dimension that keyboard events do not provide.

Keyboard events can tell us WHAT happened.

Mouse data can additionally tell us WHERE the user's interaction behavior is occurring.


3. WHY USE A HEATMAP?
=====================

A heatmap converts a large number of individual mouse events into an understandable spatial representation.

Raw data might look like:

    t=1000  x=450  y=300
    t=1010  x=455  y=302
    t=1020  x=462  y=305
    ...

This is difficult to interpret directly.

A heatmap transforms these events into something like:

    +--------------------------------------+
    | Question                             |
    |                                      |
    |             HIGH ACTIVITY            |
    |                                      |
    |                                      |
    |                              XXXXX   |
    |                              XXXXX   |
    |                              XXXXX   |
    +--------------------------------------+

The important information becomes:

- where the cursor spent time
- where the cursor repeatedly entered
- where movement was concentrated
- which areas received interaction
- whether activity occurred inside or outside expected UI regions

This makes heatmap analysis useful for discovering a suspicious spatial pattern.


4. WHY THIS APPROACH IS SUITABLE
================================

The approach has several useful properties for this problem.

4.1 It adds a spatial signal

Keyboard events do not inherently tell us where the user's attention/interactions are happening.

Mouse coordinates provide:

    X position
    Y position
    movement
    dwell
    entry/exit
    trajectory

This gives the detector a spatial dimension.

4.2 It is complementary to the existing model

The heatmap approach should NOT replace the existing keyboard/focus model.

Instead:

    Keyboard/focus model
              +
    Mouse spatial model
              +
    Test UI context
              =
    stronger behavioral evidence

4.3 It can investigate no-focus-shift scenarios

When an overlay does not cause focus to move away from the test application, focus events may provide no useful evidence.

Mouse behavior may still provide additional information if the user moves/interacts with the cursor in relation to the overlay or its surrounding area.

Important limitation:

A web page cannot observe arbitrary mouse activity occurring entirely inside another OS window/application if those events never reach the page.

Therefore, this POC is an inference mechanism, not direct OS-level overlay detection.

4.4 It can identify suspicious areas rather than requiring exact overlay detection

Instead of trying to answer:

    "Is an overlay open?"

the system can first answer:

    "Is there a region where interaction behavior is unusual?"

This is a more realistic objective for browser-level telemetry.


5. CORE CONCEPT
================

The system divides the available test area into spatial regions.

Example:

    +---------+---------+---------+---------+
    | Region  | Region  | Region  | Region  |
    |    1    |    2    |    3    |    4    |
    +---------+---------+---------+---------+
    | Region  | Region  | Region  | Region  |
    |    5    |    6    |    7    |    8    |
    +---------+---------+---------+---------+
    | Region  | Region  | Region  | Region  |
    |    9    |   10    |   11    |   12    |
    +---------+---------+---------+---------+

Every mouse event is mapped to a region.

The system can then calculate:

- event count per region
- dwell time per region
- number of entries
- number of exits
- movement distance
- average velocity
- movement frequency
- interaction density

The result is a spatial activity map.


6. TWO LEVELS OF SPATIAL ANALYSIS
=================================

The POC should consider two complementary spatial representations.

LEVEL 1: Pixel/grid heatmap

Divide the viewport into small cells.

Example:

    20 x 20 grid
    40 x 40 grid
    or dynamically sized cells

Each mouse event contributes activity to a cell.

This produces a detailed heatmap.

LEVEL 2: Semantic UI regions

Use the actual application UI to classify areas such as:

    QUESTION
    ANSWER
    OPTIONS
    NEXT_BUTTON
    PREVIOUS_BUTTON
    SUBMIT
    NAVIGATION
    BACKGROUND
    OUTSIDE_EXPECTED_UI

Semantic regions are useful because a heatmap alone does not know whether activity is expected.

For example:

    High activity in answer box = normal

    High activity in an irrelevant empty area = potentially interesting

The recommended POC uses BOTH.

9. NORMALIZATION
================

Raw screen coordinates are affected by screen size.

For example:

    Screen A:
        width = 1920
        height = 1080

    Screen B:
        width = 1366
        height = 768

The same logical location will have different pixel coordinates.

Therefore, normalize coordinates:

    normalizedX = x / viewportWidth
    normalizedY = y / viewportHeight

Example:

    x = 1440
    viewportWidth = 1920

    normalizedX = 0.75

Likewise:

    y = 540
    viewportHeight = 1080

    normalizedY = 0.50

This allows spatial behavior to be compared across different viewport sizes.


10. HEATMAP GENERATION
======================

The simplest implementation divides the viewport into cells.

Example:

    gridWidth = 40
    gridHeight = 40

Each mouse event maps to a cell.

For every event:

    cellX = floor(normalizedX * gridWidth)
    cellY = floor(normalizedY * gridHeight)

Then increment activity:

    heatmap[cellY][cellX] += 1

However, event count alone is not enough.

A mouse moving continuously through a region can generate many events.

Therefore, the POC should eventually consider time/dwell weighting.


11. DWELL-TIME WEIGHTING
========================

Suppose the mouse remains in one location for 5 seconds.

The system should recognize that this is different from quickly passing through the location.

For consecutive mouse samples:

    previous timestamp
    current timestamp

calculate:

    deltaTime = currentTimestamp - previousTimestamp

If the cursor remains in the same region, add deltaTime to that region's dwell time.

This gives:

    regionDwellTime

instead of only:

    regionEventCount

13. NORMAL UI VS SUSPICIOUS REGION
==================================

The most important part of the POC is learning what NORMAL looks like.

For example:

    Question area
        high activity -> expected

    Answer box
        high activity -> expected

    MCQ options
        high activity -> expected

    Next/Previous buttons
        activity -> expected

    Empty background area
        little activity -> expected

If a region outside expected interactive areas receives unusual activity, it becomes a candidate region for further analysis.

The system should NOT immediately classify it as an overlay.


14. SUSPICIOUS REGION SCORE
===========================

A region can be assigned a score based on multiple signals.

Example conceptual score:

    suspiciousScore =
        weightedDwell
        + weightedEntryCount
        + weightedOutsideUIActivity
        + weightedRepetition
        + weightedTimingCorrelation

The exact weights should NOT be assumed initially.

For the POC, first collect data and determine which features actually differ between normal and suspicious scenarios.

Later, the score can be learned by a machine-learning model.


15. TEMPORAL CONTEXT
====================

A static heatmap is useful but not sufficient.

Consider:

    User moves mouse into irrelevant region
            ↓
    stays for 4 seconds
            ↓
    returns to answer area
            ↓
    types a large amount of text

This sequence is more informative than the heatmap alone.

Therefore, store both:

    spatial information

and:

    temporal sequence information


16. MOUSE + KEYBOARD CORRELATION
================================

The existing keyboard model should be integrated with mouse behavior.

Example:

    Mouse enters unusual region
            ↓
    3.5 seconds dwell
            ↓
    Mouse returns
            ↓
    Typing begins
            ↓
    Answer length increases significantly

This can become a combined behavioral feature.

Possible features:

    mouseDwellBeforeTyping
    mouseDistanceBeforeTyping
    timeSinceLastMouseActivity
    timeSinceLastKeyboardActivity
    answerLengthDeltaAfterMouseActivity


17. MOUSE + ANSWER-LENGTH CORRELATION
=====================================

The existing system already considers answer length.

Combine it with spatial activity.

Example:

    Before:
        answer length = 45

    Mouse:
        unusual region dwell = 4.2 seconds

    After:
        answer length = 260

This does NOT prove external assistance.

It does, however, create a stronger behavioral signal than either event independently.


18. COPY/PASTE MUST BE HANDLED SEPARATELY
=========================================

A large answer-length increase can happen because of paste.

Therefore:

    answerLengthDelta

must not automatically be treated as suspicious.

The detector should identify/track:

    paste event
    copy event
    typing event
    answer length change

Then distinguish:

    large change caused by paste

from:

    large change occurring after a suspicious behavioral sequence


19. HEATMAP TYPES
=================

The POC can generate several visualizations.

19.1 Raw event heatmap

Shows where mouse events occurred.

19.2 Dwell heatmap

Shows where the cursor spent the most time.

19.3 Entry heatmap

Shows where the cursor repeatedly entered.

19.4 Outside-UI heatmap

Shows activity outside expected interactive elements.

19.5 Question-specific heatmap

Shows activity separately for each question.

19.6 Session heatmap

Shows the complete test session.


20. QUESTION-SPECIFIC ANALYSIS
==============================

The same screen location can have different meanings depending on the question.

For example:

    MCQ:
        options are expected interaction areas.

    Written:
        answer textarea is expected.

Therefore, heatmaps should be associated with:

    questionId
    questionType
    UI state

This prevents the detector from treating all screen activity as equivalent.


21. RECOMMENDED EVENT AGGREGATION
=================================

Do not send every mousemove event directly to the ML model.

Mousemove events can be extremely frequent.

Instead, aggregate them into behavioral events/windows.

Example:

    Raw events:

        150 mousemove events
        1 click
        80 mousemove events

    Aggregate:

        MOUSE_ENTER_REGION
        MOUSE_DWELL_3S
        MOUSE_EXIT_REGION

This reduces noise and makes the sequence more meaningful.


22. TIME WINDOW APPROACH
========================

Analyze mouse behavior in fixed windows.

Example:

    1-second window
    3-second window
    5-second window
    10-second window

For each window calculate:

    mouseDistance
    mouseEventCount
    activeRegions
    dominantRegion
    dwellTime
    outsideUIPercentage
    averageVelocity
    answerLengthDelta
    keyboardActivity

The model can then receive a sequence of these feature windows.


23. POSSIBLE ML ARCHITECTURE
============================

Because an LSTM/GRU model already exists in the project, the mouse features can eventually be integrated into a sequence model.

Possible architecture:

    Mouse events
          +
    Keyboard events
          +
    Answer behavior
          +
    UI context
          ↓
    Feature extraction
          ↓
    Time-window sequences
          ↓
    GRU / LSTM
          ↓
    Suspicious behavior probability


24. ALTERNATIVE: TWO-MODEL APPROACH
===================================

Another possible architecture is:

    Model 1:
        Mouse spatial anomaly detector

    Model 2:
        Existing keyboard/event detector

Then combine their outputs.

Example:

    Mouse model:
        suspicious region = 0.72

    Keyboard model:
        suspicious behavior = 0.31

    Combined system:
        behavioral evidence requires additional context

The combination strategy should be determined from validation data rather than manually assigning arbitrary probabilities.

The quality of the detector depends heavily on the dataset.

At minimum, collect:

    scrolling

27. GROUND TRUTH
================

Ground truth is critical.

For every POC session, the test setup should know what scenario was intentionally performed.

Example:

    Session 001 -> normal
    Session 002 -> normal
    Session 003 -> controlled suspicious interaction
    Session 004 -> normal
    Session 005 -> controlled overlay scenario

Without reliable labels, it will be difficult to determine whether the heatmap actually provides useful information.


28. WHAT THE POC SHOULD PROVE
=============================

The POC should answer these questions:

1. Can mouse data be collected reliably?

2. Can mouse coordinates be normalized across viewport sizes?

3. Can mouse activity be converted into a useful heatmap?

4. Can expected UI regions be identified?

5. Can activity outside expected UI regions be measured?

6. Do controlled suspicious scenarios produce different spatial patterns from normal sessions?

7. Which mouse features provide the strongest separation?

8. Does mouse information add value beyond the existing keyboard model?

9. Does combining mouse + keyboard + answer behavior improve detection?

10. What false-positive scenarios appear?


29. SUCCESS CRITERIA
====================

The POC should NOT initially define success as:

    "Detect every overlay."

Instead, success should mean:

    "Determine whether mouse spatial behavior contains measurable,
     repeatable information that can improve the existing detector."

Useful evaluation metrics:

    Precision
    Recall
    F1 score
    False Positive Rate
    False Negative Rate
    Detection coverage

Also measure:

    percentage of sessions with usable mouse data
    percentage of suspicious scenarios producing a spatial signal
    percentage of normal sessions incorrectly flagged


30. FALSE POSITIVE CASES TO TEST
================================

This is extremely important.

Test:

    user thinks for a long time
    user moves mouse to an empty area
    user moves mouse outside the test UI
    user uses a second monitor
    user has a large screen
    user changes browser window size
    user accidentally moves the mouse
    user keeps mouse stationary
    user does not use mouse
    user scrolls
    user reads the question before answering
    user pauses while writing
    user navigates between questions

The detector must not treat these behaviors as direct evidence of overlay usage.


31. FALSE NEGATIVE CASES TO TEST
================================

Test scenarios where the suspected behavior produces little mouse evidence.

Examples:

    user never moves mouse
    overlay interaction is keyboard-only
    overlay is opened before test
    overlay remains stationary
    user interacts with another application
    mouse activity does not reach the test page
    overlay does not overlap the browser's observable interaction area

These scenarios define the limits of the approach.


32. IMPORTANT TECHNICAL LIMITATION
==================================

Browser-level mouse tracking is NOT equivalent to OS-level mouse tracking.

If the test is running inside a browser:

    webpage
        ↓
    can observe events delivered to webpage

But an external overlay/application may:

    receive its own events
    consume the events
    operate outside the browser
    never expose its activity to the webpage

Therefore, a webpage-based heatmap can identify behavioral anomalies and suspicious spatial patterns, but it cannot guarantee detection of every external overlay.


33. SECURITY / PRIVACY CONSIDERATIONS
====================================

Only collect data necessary for the POC.

Recommended:

    normalized mouse coordinates
    timestamps
    UI region
    interaction type
    test/question context

Avoid collecting unnecessary information.

The POC should also define:

    data retention
    access control
    session identifiers
    anonymization strategy
    storage duration

If raw coordinates are not required after feature extraction, consider retaining aggregated features instead.


34. PERFORMANCE CONSIDERATIONS
==============================

Mousemove events can occur at high frequency.

Do not perform expensive processing for every event.

Recommended strategy:

    collect lightweight events
          ↓
    throttle/sample where appropriate
          ↓
    aggregate
          ↓
    calculate features
          ↓
    generate heatmap

Possible sampling strategies:

    fixed interval sampling
    distance threshold
    time threshold
    requestAnimationFrame-based collection

The exact strategy should be benchmarked during the POC.

41. WHAT NOT TO DO IN THE FIRST POC
===================================

Do NOT immediately:

    train a complex model
    assume a fixed suspicious coordinate
    classify one mouse movement as suspicious
    treat all outside-UI movement as cheating/overlay usage
    rely only on event count
    rely only on dwell time
    assume the overlay has a fixed position
    assume all users behave the same
    ignore second-monitor scenarios

First determine whether there is a measurable and repeatable signal.


42. KEY HYPOTHESIS
==================

The central hypothesis of this POC is:

    "Users interacting with an external assistance overlay may produce
     spatial mouse behavior that differs measurably from normal
     interaction with the test UI."

The POC must experimentally validate this hypothesis.

It should not be assumed to be true before testing.


43. EXPECTED RESULT OF THE POC
==============================

There are three possible outcomes.

OUTCOME A - Strong signal

Heatmaps and extracted features clearly differ between controlled normal
and suspicious scenarios.

Next step:

    Build a larger dataset and evaluate ML.

OUTCOME B - Partial signal

Some suspicious scenarios produce a useful signal, while others do not.

Next step:

    Combine mouse signals with keyboard and answer behavior.

OUTCOME C - Weak/no signal

Mouse spatial behavior is not sufficiently different.

Next step:

    Do not force the heatmap approach into production.
    Use the results to identify which additional telemetry is required.

45. CONCLUSION
==============

The mouse heatmap approach is a useful POC because it introduces a dimension
that the current keyboard/focus detector does not have: SPATIAL BEHAVIOR.

The core value is not the heatmap image itself.

The real value is the features extracted from spatial behavior:

    WHERE
    HOW LONG
    HOW OFTEN
    HOW FAST
    WHEN
    WHAT HAPPENED BEFORE
    WHAT HAPPENED AFTER

These can be combined with the existing keyboard, answer-length, typing,
and UI-context signals.

The recommended strategy is therefore:

    1. Collect mouse telemetry.
    2. Normalize coordinates.
    3. Generate heatmaps.
    4. Divide activity into spatial and semantic regions.
    5. Calculate dwell/entry/movement features.
    6. Correlate mouse behavior with keyboard and answer behavior.
    7. Build a labeled POC dataset.
    8. Evaluate false positives and false negatives.
    9. Determine whether mouse features add measurable signal.
    10. Integrate validated features into the existing sequence model.

The POC should ultimately answer one practical engineering question:

    "Does mouse spatial behavior provide enough additional information
     to improve detection in scenarios that the current keyboard/focus
     approach cannot reliably observe?"

If the answer is yes, the heatmap features can become another input to the
existing detection pipeline. If not, the POC still provides evidence about
the limitations of mouse-based detection and helps determine what telemetry
is needed next.
